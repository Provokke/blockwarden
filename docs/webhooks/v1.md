# Blockwarden webhook payload, version 1

This is a public interface. It changes only with a major version of `@blockwarden/relayer-client` and a new
number in `specVersion`. Fields are only ever added inside a version; nothing is removed or retyped.

## Request

`POST` to the URL on the action, with `content-type: application/json`, from an AWS Lambda function in the
operator's own account. Redirects are not followed, so the URL has to be the final one. Only `https` is accepted.

| Header | Value |
|---|---|
| `X-Blockwarden-Signature` | `t=<unix seconds>,v1=<hex HMAC-SHA256 of "<t>.<raw body>">`. Several `v1=` values appear while a secret is rotating; any one of them matching is a valid signature. **The timestamp lives here, in `t`. There is no separate timestamp header.** |
| `X-Blockwarden-Delivery` | The delivery id, the same string as `id` in the body. It is **not covered by the signature**: treat it as a convenience for tracing and logging, and dedupe on `id` in the verified body instead. |
| `User-Agent` | `Blockwarden/1` |

A webhook action may rename both headers (`signatureHeader`, `deliveryHeader`), so a receiver sees its own
product's name. The format of the values does not change. The two names have to be different headers, compared
without case and counting the default of a name that is left out: one name for both would put the delivery id
where the signature goes, and an action that asks for it is refused rather than delivered unsigned.

`verifyWebhook()` accepts a timestamp **within 300 seconds** of now, in either direction, and that is what the
sender's own tests assert. A receiver that sets its own tolerance should not go above 900 seconds: a delivery
that has waited longer than that has been retried, and its `t` is the time of the attempt, not of the event.

## Body

```json
{
  "id": "dlv_9a1c...",
  "type": "match.final",
  "createdAt": "2026-09-20T10:19:03.114Z",
  "specVersion": 1,
  "data": { }
}
```

| Field | Type | Meaning |
|---|---|---|
| `id` | string | The delivery id, `dlv_` and 32 hex characters. Unique per attempt-group: every status change gets its own id, so a transaction that is reorged out and mined again sends a second `tx.mined` with a **different** id. Retries of one delivery reuse the id. |
| `type` | string | `match.provisional`, `match.final`, `match.dropped` or `tx.<status>` where status is one of `queued`, `submitted`, `mined`, `confirmed`, `failed`, `cancelled`. |
| `createdAt` | string | When the delivery was created, not when this attempt was sent. ISO 8601 with milliseconds, always UTC. |
| `specVersion` | number | `1`. Absent only from a body sent by a version of Blockwarden older than this document. |
| `data` | object | The event body, below. |

### `data` for `match.*`

Every numeric value inside `args` is a **decimal string**, because a uint256 does not fit in a JSON number.
That holds for a small integer too: an `int24` or a `uint8` decodes to a JS number, and the sender converts it
before it sends, so a receiver never has to handle two forms of the same field. Numbers that are always
small — `chainId`, `blockNumber`, `logIndex`, `ordinal` — are JSON numbers.

| Field | Type | Notes |
|---|---|---|
| `matchKey` | 32-byte hex string | `keccak256(chainId, transactionHash, ordinal, ruleId)`. Stable across a provisional record and its final one. |
| `ruleId` | string | |
| `status` | `provisional` \| `final` \| `dropped` | |
| `chainId` | number | |
| `address` | 20-byte hex string | The contract that emitted the log, exactly as the node returned it. Most nodes answer in lowercase, but that is not promised and Blockwarden does not rewrite it, so the same address can arrive checksummed. Compare it case-insensitively — `isAddressEqual` in viem, or lowercase both sides — never with `===`. |
| `transactionHash` | 32-byte hex string | |
| `blockNumber` | number | |
| `blockHash` | 32-byte hex string | The block the log was recorded in. A provisional record's block can differ from its final one's. |
| `logIndex` | number | Within the block. |
| `ordinal` | number | The log's position among the logs of the same transaction, block and rule. |
| `event` | string | The rule's event signature, for example `event Transfer(address indexed from, address indexed to, uint256 value)`. |
| `eventName` | string | `Transfer`. |
| `args` | object | Decoded arguments by name. A tuple is an object, an array is an array, and both nest. Addresses and bytes are hex strings, `bool` is a JSON boolean, every integer is a decimal string. |
| `firstSeenAt` | string | When the match was first recorded. |
| `finalizedAt` | string \| null | When it became final; `null` while provisional or dropped. |

A `fast` rule sends `match.provisional` when the log is first seen in an unfinalized block, then exactly one of
`match.final` or `match.dropped`. A `finalized` rule sends only `match.final`. A dropped match's log was reorged
away, and nothing it described happened.

### `data` for `tx.*`

The transaction exactly as `GET /v1/relayer/txs/{txId}` returns it. `value` and `gasLimit` are decimal strings,
because a wei amount does not fit in a JSON number. Every field is always present; the nullable ones carry
`null` rather than being left out.

| Field | Type | Notes |
|---|---|---|
| `txId` | string | |
| `kind` | `relay` \| `filler` | A filler is the 0-value self-transfer that takes the nonce of a transaction that failed after its nonce was reserved. |
| `signerId` | string | |
| `chainId` | number | |
| `from` | hex string | The signer's address. |
| `to` | hex string | |
| `data` | hex string | The calldata, of any length. |
| `value` | string | Decimal wei. |
| `gasLimit` | string | Decimal. |
| `status` | string | One of `queued`, `submitted`, `mined`, `confirmed`, `failed`, `cancelled`. |
| `nonce` | number \| null | `null` until a nonce is reserved. |
| `hash` | hex string \| null | The latest signed hash; once mined, the hash that was mined. `null` until something is signed. |
| `blockNumber` | number \| null | `null` until mined. |
| `blockHash` | hex string \| null | `null` until mined. |
| `receiptStatus` | `success` \| `reverted` \| null | `null` until mined; a mined transaction can still have reverted. |
| `error` | string \| null | Why it failed; `null` while nothing has gone wrong. |
| `revertData` | hex string \| null | The raw revert data when the transaction failed because its call reverts; `null` otherwise. A sender older than `@blockwarden/relayer-client` 0.2.0 leaves the field out altogether, and `parseTx` reports that as `null`. |
| `fillerTxId` | string \| null | On a failed transaction, the filler that took its nonce; `null` otherwise. |
| `idempotencyKey` | string \| null | The caller's key; `null` on a transaction Blockwarden sent itself, such as a filler. |
| `reference` | string \| null | The caller's own string, echoed; `null` when none was given. |
| `dependsOn` | string \| null | The earlier `txId` this one waited for; `null` when none was given. |
| `createdAt` | string | |
| `updatedAt` | string | |

Use `isTxEvent(event)` and `parseTx(event.data)` from `@blockwarden/relayer-client` to read one with bigints.

## Answering

Answer `2xx` and nothing is retried. Any other status, or no answer at all, is an attempt that failed:

- `3xx` is permanent. A redirect is never followed, so the delivery is dead-lettered at once: point the action
  at the final URL rather than at anything that redirects to it.
- `4xx` other than `429` is permanent. The delivery is dead-lettered at once, with no further attempt.
- `429` and `5xx` are retried, as are a timeout, a connection failure and a TLS failure.
- Up to **8 attempts**, about 10 s, 30 s, 90 s, 270 s and then 9 to 15 minutes apart, jittered, never more
  than 900 s apart, then dead-lettered. A delivery that never succeeds is dead about 43 minutes after it was made.

An answer has **10 seconds** of socket silence and **15 seconds** in total to arrive, whichever comes first. A
receiver that takes longer sees the attempt abandoned and retried even if it went on to answer 200, so do the
work after answering rather than before.

The body of the answer is read only for an operator's logs, at most 2 KB of it.

## What is not guaranteed

The delivery is **at least once**. A crash between claiming a delivery and sending it, an SQS redelivery, or the
reaper picking up a delivery whose attempt is still in flight can all send the same body twice with the same id.
Dedupe on `id` from the body `verifyWebhook()` returned: it is inside the signed bytes, so a replay cannot change
it, while `X-Blockwarden-Delivery` is an unsigned header anyone forwarding the request can rewrite. The two carry
the same value. Two different deliveries never share an id.

Order is not guaranteed either. `match.final` can arrive before `match.provisional` if the first attempt of the
provisional one failed. Compare `data.status`, not arrival order.
